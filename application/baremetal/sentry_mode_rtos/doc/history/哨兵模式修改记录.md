# 哨兵模式修改记录

**日期**: 2026-04-27
**范围**: sentry_mode_rtos 项目代码审查与修复

> 每条记录按统一结构：**问题点 → 为什么需要修改 → 修改的原理**

---

## 一、文档对比修正（设计文档 v4.0 vs 集成记录 v1.0）

### 1.1 警报任务栈大小矛盾

**问题点**：设计文档内部三处数据打架——§2.2 表格写 2KB，§3.1.6 写 16384 字节（16KB），§3.1.2 代码写 `[4096]`（16KB）。三者互不一致。

**为什么需要修改**：文档是代码的唯一规格来源。不一致会导致后来者不知道该信哪个，可能在配置 FreeRTOS 静态内存时错误分配。

**修改的原理**：读 `tasks.c` 中 `task_alarm_handler()` 实现——极简任务，仅在等通知→GPIO→延时 30s→关 GPIO，无大局部变量。结合 `StackType_t = 4 字节`，取 2048 words = 8KB，折中大小。同步修改 main.c 和两份文档中所有相关数值。

### 1.2 L1 功耗数据矛盾

**问题点**：§3.6.1 表格 L1 功耗写 ~20mW，§7.5 写 8mW。

**为什么需要修改**：两份文档描述同一系统，功耗数值必须一致，否则无法准确评估电池续航。

**修改的原理**：§7.5 有明确推导公式——`80mW×4%（活跃）+ 5mW×96%（休眠）= 8mW`，物理意义完备。§3.6.1 无任何推导依据，推测为首版方案残留。以 §7.5 计算模型为权威来源，统一为 ~8mW。

### 1.3 CPU 位数描述

**问题点**：硬件表格写 "N600FD / NX600FD | 32位"，编译命令用 `CORE=n600fd`（32 位 CORE），架构说明写 `rv32imafdc`（32 位 ISA）。实际 RTOS 跑在 NX600FD（64 位）处理器上。

**为什么需要修改**：文档声称的平台与实际硬件不一致，导致编译参数（CORE/ARCH/ABI）全错，编译产物无法在真实硬件上运行。

**修改的原理**：N600FD 是 32 位处理器（rv32），NX600FD 是 64 位处理器（rv64）。实际硬件是 NX600FD，所以全文 14 处从 32 位描述统一改为 64 位：CORE → `nx600fd`，架构 → `rv64imafdc_xxldsp`，ABI → `lp64d`。RISC-V 64 位模式下 `long` 和指针变为 8 字节，但 `StackType_t` 在 FreeRTOS 端口实现中固定为 `uint32_t`（4 字节），不受此改变影响。

### 1.4 Tensor Arena 早期估值

**问题点**：设计文档 §3.7.7 注解说早期估算是 80KB，集成记录 §3.2.2 记录的代码变更是从 `100*1024`（100KB）改到 `1024*1024`（1MB）。

**为什么需要修改**：集成记录是实测代码变更日志，权威性高于设计文档的回忆性注释。

**修改的原理**：以集成记录为权威来源，将 80KB 修正为 100KB。最终 1MB 是实测 SSD MobileNet v2 FPN-lite 0.35 @ 224×224 推理所需张量缓冲的真实大小。

### 1.5 文档尾部版本号

**问题点**：设计文档头部声明 v4.0，尾部写 v3.0。

**为什么需要修改**：版本号不一致是明显的文档维护遗漏。

**修改的原理**：以头部 v4.0（2026-04-25）为准更新尾部。

## 二、代码 vs 文档三方对比修正

### 2.1 Makefile CORE 值

**问题点**：Makefile 写 `CORE = n600fd`，与文档中已修正的 `nx600fd` 不一致。

**为什么需要修改**：Makefile 是编译的唯一入口，CORE 值决定了 CPU 系列选择、架构字符串生成和最终指令集。与文档和硬件不符的 CORE 值会导致编译产物无法运行。

**修改的原理**：`n600fd` 对应 Nuclei 600 系列 32 位处理器，`nx600fd` 对应 64 位。同步修改注释和变量值。Makefile 构建系统会根据 CORE 值自动推导 `RISCV_ARCH` 和 `RISCV_ABI`。

### 2.2 任务栈字节数

**问题点**：文档声称 AI/Recorder/Writer 任务栈为 4KB（4096 字节），Monitor 为 2KB。但代码中 `s_task_ai_stack[4096]` 的 4096 是 `StackType_t` 元素数，每个元素 4 字节，实际为 16KB。文档将"元素数"误当作"字节数"。

**为什么需要修改**：FreeRTOS 在创建任务时使用元素数计算栈大小（见 `xTaskCreateStatic` 的栈深度参数）。文档写 4KB，但 DLM 实际被占用 16KB。如果不修正，DLM 的 64KB 总容量会被严重低估，导致后续分配溢出。

**修改的原理**：`StackType_t` 在 FreeRTOS RISC-V 端口定义为 `uint32_t`，始终 4 字节。每处标注从 `4096字节` 修正为 `16384字节 (4096 words)`。Monitor 从 2KB 修正为 8KB（2048 words × 4 bytes）。

### 2.3 memory_manager.c Tensor Arena 局部覆盖

**问题点**：`memory_manager.c` 第 19 行 `#define DDR_TENSOR_ARENA_SIZE (100 * 1024)` 局部重定义了头文件 `sentry_mode.h` 中的 `(1024 * 1024)`，导致本文件内分配的 Tensor Arena 只有 100KB，而非需要的 1MB。

**为什么需要修改**：C 预处理器中局部 `#define` 覆盖头文件宏不会报错，属于静默 bug。如果有代码通过 `memory_manager.c` 的 `get_tensor_arena()` 获取并使用了这个仅 100KB 的缓冲区进行 1MB 的推理，将导致内存越界，运行时崩溃。

**修改的原理**：删除局部 `#define`，让头文件的 `DDR_TENSOR_ARENA_SIZE (1024 * 1024)` 通过 `#include "sentry_mode.h"` 正常透传。C 预处理器按文件处理顺序展开宏，去掉局部定义后自然使用头文件值。

### 2.4 camera_capture_rgb64 旧接口名

**问题点**：设计文档 §4.1.2 列出 `camera_capture_rgb64(uint8_t* buffer)`，但代码中实际接口是 `camera_capture_rgb(uint8_t*, int width, int height)`。

**为什么需要修改**：集成记录 §3.5.1 已记录了旧版 `rgb64`（固定 64×64）到新版 `rgb(w,h,buf)` 的演进。设计文档是正式 API 规格，应反映当前接口。

**修改的原理**：文档接口定义同步为 3 参数版本，与代码 `hal.c` 中的实现签名一致。

### 2.5 NMS IoU 阈值

**问题点**：代码 `ai_engine.cpp:125` 中 NMS 的 IoU 阈值为 `0.4f`，文档 §3.4.2 写为 0.5。

**为什么需要修改**：代码是实际运行的行为来源，文档应与代码一致。

**修改的原理**：NMS（非极大值抑制）中 IoU 阈值控制两个检测框重叠多少时视为重复。0.4 比 0.5 更宽松（保留更多框），适合嵌入式低功耗场景中容忍一定冗余以提高召回率。

### 2.6 LEVEL1_DETECTION_THRESHOLD 命名误导

**问题点**：宏名叫 `LEVEL1_DETECTION_THRESHOLD`（检测阈值），值却是 `0.25f`，实际用于 NMS 粗筛。真正判定"检测到人"的阈值是 tasks.c 中硬编码的 `0.6f`。该宏从未被用于最终的检测判定。

**为什么需要修改**：命名误导维护者——如果将来有人调高这个宏期望减少误报，会发现它对最终检测结果没有影响。硬编码的 `0.6f` 和宏定义的 `0.25f` 的职责差异需要明示。

**修改的原理**：重命名为 `NMS_CONFIDENCE_THRESHOLD`，准确反映其职责——在 NMS 前过滤掉置信度低于 0.25 的候选框以减少 NMS 计算量。真正的检测逻辑走 `tasks.c` 中的 `conf > 0.6f` 判定。

### 2.7 @file 注释未更新

**问题点**：文件已从 `ai_engine.c` 重命名为 `ai_engine.cpp`，但顶部 Doxygen `@file` 注释仍写 `.c`。

**为什么需要修改**：文档注释不准确的细节积累会降低代码库的可信度。

**修改的原理**：直接修正为 `.cpp`，与文件扩展名一致。

## 三、栈溢出修复

### 3.1 问题总述

AI 任务栈 16KB、录制任务栈 16KB、写入任务栈 16KB。但各任务函数中存在超大局部数组——L1 推理帧 147KB、L2/L3 时序输入 96KB、录制/写入帧各 150KB。编译器将局部数组分配在栈上，远超栈容量。

**为什么需要修改**：栈溢出在嵌入式系统中不会产生友好错误——栈向下扩展会覆盖相邻的数据段（如 DLM 中的任务 TCB 或队列缓冲区），导致不可预测的崩溃。这是运行时必定触发的致命 bug。

### 3.2 修改原理

将所有局部数组提升为文件级 `static` 变量，通过 `__attribute__((section(".ddr_bss")))` 放置在 DDR 的 `.ddr_bss` 段。

**为什么可以这样做**：

1. DDR 有 512MB+ 空间，总计 ~434KB 开销可忽略
2. L1/L2/L3 分支是互斥的——同一任务永远只执行其中一个分支，所以 `s_level1_frame` 和 `s_level23_frame` / `s_temporal_input` 虽然同时存在，但不会同时被使用
3. FreeRTOS 静态分配的 `static` 变量在编译时确定，无运行时初始化开销
4. L2 与 L3 共享 `s_level23_frame` 和 `s_temporal_input`，进一步节省内存

## 四、并发保护

### 4.1 g_stats 无锁保护 → g_stats_mutex

**问题点**：`g_stats` 结构体的 9 个计数字段被 5 个不同优先级的任务通过 `++` 操作修改。`g_stats.level1_frames++` 在 RISC-V 上编译为 load-add-store 三条指令，抢占可导致计数永久丢失。

**为什么需要修改**：虽然 `g_stats` 仅为调试统计，但数据损坏会让运维日志不可靠——无法准确判断系统触发了几次警报、丢了多少帧。

**修改的原理**：引入 `g_stats_mutex` 互斥锁。单个计数字段写操作用 `Take-操作-Give` 保护，监控任务的 9 字段批量读取用一次 Take/Give 包裹。Mutex 利用 FreeRTOS 的优先级继承机制——如果高优先级任务（AI prio3）等锁，持有锁的低优先级任务（Writer prio1）会临时提升优先级，防止优先级反转。

### 4.2 s_fil 文件句柄共享 → g_fil_mutex

**问题点**：Recorder（prio2）负责 `f_open` 和 `f_close`，Writer（prio1）负责 `f_write`，两者共用同一个 `s_fil` 句柄。当 Recorder 调用 `f_close` 时，队列中可能还有未处理的帧，Writer 将对已关闭的文件句柄执行 `f_write`——触发未定义行为。此外 FatFs 的 `FIL` 结构体不是可重入的——Recorder（prio2）可在 Writer（prio1）的 `f_write` 执行中间抢占。

**为什么需要修改**：文件系统损坏会导致视频证据丢失——这正是哨兵模式最核心的功能。

**修改的原理**：
1. `g_fil_mutex` 互斥锁保护所有 `s_fil` 操作（`f_open`、`f_write`、`f_close`）
2. `f_close` 前增加队列 drain——`while (uxQueueMessagesWaiting(g_frame_queue) > 0) { vTaskDelay(1); }`——确保 Writer 已消费完所有帧

### 4.3 AI 引擎无保护 → g_ai_mutex

**问题点**：Alarm 任务（prio4）在警报 30 秒结束时调用 `ai_switch_mode(MODE_LEVEL1)`。这可以抢占正在执行推理的 AI 任务（prio3），修改 AI 引擎的 `s_current_mode` 变量。当前 `ai_switch_mode` 实现只是一个赋值，但接口设计保留了未来扩展模型重载等复杂操作的可能。

**为什么需要修改**：缺乏并发保护使 AI 引擎的所有内部状态（模型指针、张量、检测结果）暴露给竞态条件。即使现在只是赋值操作，这也是不合规的 API 设计——接口的并发安全性不应依赖调用者的"自觉"。

**修改的原理**：`g_ai_mutex` 保护 6 个 `extern "C"` 接口函数——`ai_init`、`ai_switch_mode`、`ai_run_inference`、`ai_get_detection_result`、`ai_get_confidence`、`ai_get_detection_boxes`。每个函数的入口加锁、出口（含所有 return 点）解锁。推理函数中互斥锁的持有时间覆盖了整个 `Invoke()` 调用（~50-100ms），确保推理期间模型状态不被修改。

### 4.4 相机采集冲突 → g_camera_mutex

**问题点**：AI 任务（L2/L3，每 200ms）和 Recorder 任务（每 33ms）同时调用 `camera_capture_*`。在单路相机硬件上，DMA 通道只有一个，两个并发调用会导致硬件冲突。

**为什么需要修改**：硬件不支持并行采集且无并发保护时，两个 DMA 请求会互相覆盖，导致双方都拿到错误数据——AI 推理结果错误，录像帧花屏。

**修改的原理**：`g_camera_mutex` 互斥锁序列化所有相机采集操作。Recorder 优先级（prio2）低于 AI（prio3），但利用 FreeRTOS 优先级继承——Recorder 持锁时 AI 等待，Acquire 的 33ms 周期天然让 Recorder 在大多数时间持有锁。AI 仅在每 200ms 的推理窗口拿锁，拿完立即释放。

## 五、CMD_STOP_RECORDING 发送者

**问题点**：代码中只有接收方（Recorder 第 456 行 `else if (cmd.type == CMD_STOP_RECORDING)`），没有任何任务发送此命令。录制一旦启动，只能等 30 秒自然结束，无法被状态机中断。同时 AI 从 L2/L3 退出进入休眠时调用 `camera_power_down()`，而 Recorder 仍在录——导致 Recorder 调 `camera_capture_yuv320` 全部静默失败。

**为什么需要修改**：这两个问题是因果链——缺少停止命令直接导致了摄像头竞争（并发 #4）。此外无法中断录制是功能缺陷——危险解除后系统应能立即省电，而不是干等 30 秒。

**修改的原理**：在 AI 任务的 5 个 L2/L3 退出点各添加：
1. `xQueueSend(g_cmd_queue, &{CMD_STOP_RECORDING}, 0)`——投递停止命令
2. `vTaskDelay(pdMS_TO_TICKS(50))`——让出 CPU 给 Recorder（prio2），确保它收到命令并设置 `s_recording = false` 后才继续执行

50ms 延迟的选择依据：Recorder 在 `xQueueReceive` 上阻塞，AI 发完命令后主动让出 CPU，FreeRTOS 调度器会立即切换到就绪的 Recorder。处理 `CMD_STOP_RECORDING` 只需几微秒，50ms 绰绰有余。

## 六、内存去重与死代码

### 6.1 s_frame_history 三份拷贝

**问题点**：`s_frame_history[98KB]` 在 main.c、memory_manager.c、tasks.c 各定义了一份独立副本。只有 tasks.c 的副本被实际使用。此外 tasks.c 的副本没有 `.ddr_bss` 属性，98KB 进入默认 BSS 段，在仅有 64KB DLM 的平台上会溢出。

**为什么需要修改**：浪费 196KB DDR（两份未使用的副本），且 tasks.c 的 BSS 版本会导致链接错误或静默内存损坏（BSS 段排布在 DLM 中，超出 64KB 上限）。

**修改的原理**：删除 main.c 和 memory_manager.c 的 `s_frame_history` 声明及 `get_frame_buffer()` 函数。给 tasks.c 的唯一保留副本添加 `.ddr_bss` 属性，确保 98KB 放在 DDR 而非 DLM。

### 6.2 死代码——重复 STATE_SLEEP 分支

**问题点**：`tasks.c` 的状态机中存在两个 `else if (current_state == STATE_SLEEP)` 分支。第一个在判定链的开头，第二个在 L1 分支之后。由于 `current_state` 是函数内捕获的局部变量，第一个分支已处理 SLEEP 状态，第二个永远无法执行。

**为什么需要修改**：死代码增加维护负担——后来者可能误以为第二个分支有特殊用途而修改它，但实际上它永远不会被执行。

**修改的原理**：直接删除第二个 `STATE_SLEEP` 分支（包含状态变更和信号量操作），不改变程序行为。

## 七、DCP 配置

**问题点**：DCP 默认压缩阈值为 `minContextLimit=50000`、`maxContextLimit=100000`，设计目标为 ~200K 上下文窗口的模型。当前使用 deepseek-v4 支持 100 万 token 上下文，默认阈值过于激进——不到 10% 就开始提醒压缩。

**为什么需要修改**：过早的压缩提醒干扰工作流，且 100K 阈值在 100 万上下文中仅占 10%，浪费大量可用上下文空间。

**修改的原理**：`minContextLimit → 300000`（30% 起提醒），`maxContextLimit → 700000`（70% 强制压缩），`nudgeFrequency → 20`（降低提醒频率）。DCP 的 `nudgeForce: "soft"` 保持柔和模式不变。
